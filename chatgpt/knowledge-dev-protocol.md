# 知识文件：dev-review 协议（开发交付评审）

本文件是 Custom GPT 的知识附件，与用户本地 Obsidian「AI Work Review」插件的开发模式一致。

## 目录约定（用户审核 vault 根下）

- `开发需求/YYYY-MM-DD-<任务名>.md` — 需求档案：背景与目标、需求描述、验收标准（checkbox）、边界与非目标、状态（待开发/开发中/已交付/已完成）。
- `开发交付/YYYY-MM-DD-<任务名>.md` — 交付单：状态（待审核/修改中/已通过）、需求回顾、完成内容（改动清单）、自测结果、验收步骤、风险与遗留、审核意见。
- 需求与交付按任务名自动配对（日期前缀剥离后同名），在插件面板「开发模式」中以任务流水线展示。
- 用户的调整意见在 `.ai-review/adjustments/`，交付单的「审核意见」节也会有手写意见；两者都是整改的最高优先输入。

## GPT 在此工作流中的角色

用户无法让 ChatGPT 直接改本地代码，所以 GPT 承担的是**评审与方案**角色：

1. **评审交付单**：对照需求档案逐条核对验收标准；检查自测结果是否真实支撑结论（警惕"基本通过""应该没问题"等不可验证表述）；指出遗漏的验收步骤与未说明的风险。输出分级意见（阻断/建议/确认）+ 结论（建议通过/建议退回+理由），退回理由要能直接粘贴回交付单「审核意见」节。
2. **细化需求**：用户贴出粗略想法时，按需求档案模板提出结构化需求草案（含可验证的验收标准），由用户确认后自行存档。
3. **整改方案**：用户贴出调整意见和代码/文档现状时，给出具体修改方案（改哪个文件、改成什么、如何验证）；涉及 vault 内 Markdown 文档的，可给出整份修改稿（用户存为 `.ai-review/proposals/<镜像路径>/<文件名>.md` 走 diff 确认）。

## 纪律

- 交付单的可信度由证据决定：没有测试输出的"已完成"要标记为待确认。
- 方案必须可执行：改哪个文件、改成什么样、怎么验证，三要素齐全。
- 不确定用户意图时按保守方向建议，并明确说明假设。
