# 参考文件：文档检查（报告闭环）

检查报告格式、六项检查与整改规则的正本（`组件比对` 的报告格式与整改纪律同以本文件为准）。单源：改细则只改本文件，改完按「技能正本规则」同步项目副本。

## 文档检查 \<模块|整改\>

开发文档**规范检查**闭环：**检查出报告 → 按报告整改 → 改完删报告**。检查只写报告不改文档；整改只按报告逐项修文档，**一律不动状态**（状态纠偏走面板按钮）。业务文档、页面卡、组件卡的漂移（含**页面布局图**缺卡/槽位漂移）归 `组件比对`——它同样出报告 `docs/组件文档/_比对报告.md`，不在这里重复。

**检查**（无参数＝全库，或点名模块）：按下列六项扫 `docs/开发文档/` 全部任务文档（含微改档案；发现旧 `开发需求/`、`开发交付/` 未迁移档案，列入待迁移），发现写入报告 `docs/开发文档/_检查报告.md`（`_` 前缀＝非任务文件，插件不当任务扫；每次检查**覆盖重写**，以最新扫描为准），并在对话里给摘要。条目归档（`docs/归档/<模块>/`）不做全量检查，只查两小项：原文档指针指向的归档文件是否存在（死链进⑤）、归档内有没有滞留的未处理条目（有＝搬回正文对应节）。

```markdown
# 文档检查报告

- **时间**：YYYY-MM-DD HH:mm
- **范围**：全库 / <模块>
- **统计**：违规 n 项（AI 可修 a / 需作者定夺 b）

## 待整改（AI 可修）

- [ ] <模块>/<文件名>｜<检查项>：<事实> → <修法>

## 需作者定夺

- [ ] <模块>/<文件名>｜<检查项>：<事实> → <作者动作>
```

六项检查（①②③进「待整改」，④⑤及存疑的⑥进「需作者定夺」）：

1. **基本信息**（插件状态机与 `整合` 的锚点）：状态 / 模块 / 目标目录 / 来源 / 提出日期 / 交付日期 六字段齐全；状态取值在八个合法值内；**交付日期只允许 `交付` 填**——待审核/调整中/已通过/开发中 却有交付日期＝预填（面板主按钮会变「完结」、跳过审核门）：交付节为空的归「待整改」（清空安全），有实质内容的归「需作者定夺」（可能真交付过）；微改档案 `来源` 应为 `微改`。字段缺失可从路径/文件名推断的（模块/目标目录/提出日期）归「待整改」，状态/来源拿不准的归「需作者定夺」。
2. **微改档案结构**：应含 基本信息/需求描述/验收标准/交付 四节，缺节＝违规（补空节）；多出的章节不罚。
3. **条目格式**（面板统计与「撤回」依赖）：补充需求每条 `- （YYYY-MM-DD HH:mm）…`；缺陷记录/需求变更每个条目 `### YYYY-MM-DD HH:mm` 块＋bullet＋`- **整改**：`／`- **落实**：` 占位；时间戳可解析；条目最新在前（节标题后第一条＝最新）。格式坏的条目会让 pending 统计与撤回**静默失效**——修复只排格式与归位，不改条目内容。正文节里「落实／整改」已填的条目＝未归档滞留 → 归「待整改」，修法＝原样移入条目归档文件（见 `references/templates.md`「模板：条目归档」）＋节尾指针行；节尾指针行必须是 `> 已完成条目归档：[[<文档名>-归档]]` 引用行，写成列表行的一并修正。
4. **状态与条目一致性**（漂移，作者定夺）：「整改中」但缺陷记录没有未整改条目、或有未整改条目却不在整改中；「变更中」但需求变更全部已落实；「完结」但交付节为空 → 面板按钮纠偏。
5. **双链健康**（作者定夺）：正文的 `[[概念]]` 死链（`docs/公用配置/` 无对应卡）＝概念未沉淀或拼错 → `建卡` 或改链；`优先复用：[[组件]]` 指向不存在的组件卡；条目指针 `[[<文档名>-归档]]` 死链（归档文件被删/改名，AI 无法重建）→ 需作者定夺。
6. **微改滥用提示**（不算违规）：同模块同目标目录连续多份微改档案 → 提示攒批或改走 `需求`，写进报告备注。

**整改**（参数＝`整改`）：读 `_检查报告.md`——报告不存在就如实说明，先跑检查；不要凭记忆整改。

1. 逐项处理「待整改」：缺节按模板补空节、可推断字段补齐、交付节空则清空预填的交付日期、条目格式按面板同款修复。每修一项把 checkbox 改 `[x]` 并在行尾补「（已修：<做了什么>）」。
2. 「需作者定夺」项**不代做**：列出待作者处理（面板纠偏 / 核实日期 / 建卡）。
3. 「待整改」全部勾完、且作者确认定夺项已处理 → **删除报告文件**；仍有未处理项 → 保留报告，如实汇报卡在哪些项。
