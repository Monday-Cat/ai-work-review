# /dev-review 说明书

**这是什么**：统一开发文档工作流，与 Obsidian「AI Work Review」插件开发模式配合。需求与交付写在**同一份**开发文档里：AI 写需求 → 你在面板「通过 / 调整」→ AI 开工、交付 → 你「完结」。状态与指令一一对应：**调整中**→`调整`（只改文档）、**变更中**→`变更`（只落地代码）、**整改中**→`整改`（只修 BUG）。对过代码以后改需求走两步：记「需求变更」→调整中→`调整` 定稿 →变更中→`变更` 落地。

## 命令用法

| 命令 | 时机 | 作用 |
|---|---|---|
| `/dev-review 解析模块` | 首次接入 | 扫描 `lib/features/` 每个业务目录，建 `docs/开发文档/<模块>/` 与模块卡 `_模块.md`（结构索引） |
| `/dev-review 解析业务 <模块> [流程]` | 读懂某个模块 | 把该模块现有业务按业务线拆成开发文档（快照，状态=完结；带 `流程` 则待审核，走审核-开工闭环） |
| `/dev-review 深度拆解 [模块…] [更新]` | 读懂整个项目 | **逐模块串行**解析全部业务：拆完一个（写盘 + 模块卡标记）再下一个；中断后重跑自动续；默认增量，带 `更新` 强制重拆 |
| `/dev-review 需求 <任务描述>` | 开工前 | 把对话需求转写成开发文档（验收标准 checkbox、边界与非目标），状态=待审核 |
| `/dev-review 调整` | 文档状态「调整中」 | 按新需求重新生成文档（只改文档）：需求阶段→待审核；对过代码→变更中 |
| `/dev-review 开工` | 你点「通过」后 | 对「已通过」的文档改代码，状态=开发中；动代码前先读模块卡「缺陷史」防复发 |
| `/dev-review 交付 <任务>` | 功能做完 | 对照验收填同一文档「交付」节，状态=已交付；自测含对照缺陷史的回归检查 |
| `/dev-review 整改`（别名 `添加BUG`） | 你写下 BUG 后 | 只读文档「缺陷记录」里已有条目并修，不新开文档；补「整改」「根因」并汇入模块卡「缺陷史」 |
| `/dev-review 变更` | 文档状态「变更中」 | 文档已定稿，按文档落地代码、补「落实」，写回同一文档 |
| `/dev-review 继续` | 已交付被调整后 | 落实调整意见（代码 + 交付节），重新交复审 |
| `/dev-review 状态` | 随时 | 按模块列出所有文档卡在哪一步、下一步该谁 |
| `/dev-review:info-cn` / `:info-en` | — | 显示本说明书（中/英文） |

## 文件去向

| 位置 | 内容 | 说明 |
|---|---|---|
| `docs/开发文档/<模块>/` | 开发文档（需求+交付同文件） | 审核对象；状态字段被插件跟踪 |
| `docs/开发文档/<模块>/_模块.md` | 模块卡（结构索引） | 记录分层 / 页面 / 职责 / 业务拆解进度与「缺陷史」（已修复缺陷的根因索引，开工/变更/交付前先读）；不是任务，不可开工 |
| `.ai-review/adjustments/` | 面板「调整」写的意见 | 技能处理时优先读取，处理后自动清除 |

## 工作闭环

```
（可选）深度拆解 / 解析业务 → 读懂现状
/dev-review 需求 → Obsidian 开发模式审：「调整」按新需求重新生成文档 / 「通过」放行
→ /dev-review 开工 → /dev-review 交付 → 你点「完结」
→ 对过代码以后改需求：点「需求变更」→ 调整中 → /dev-review 调整 定稿 → 变更中 → /dev-review 变更 落地代码（AI 忘了改成「变更中」时，面板点「定稿」补上）
→ 是 BUG 点「缺陷」→ /dev-review 整改
```

## 核心规则

1. 需求与交付诚实：测试没过就写没过——你靠文档做批准决策。
2. 状态机把门：只有「已通过」能开工；业务快照固定「完结」，不会被误开工。
3. 业务解析文档必须能对照代码：页面入口、主流程、业务规则、分支异常、数据依赖，读不准的标假设。

## 适用范围

技能装在项目内（ZCode：`.zcode/skills/`；Cursor：`.cursor/skills/`），管理**本项目**的 `docs/开发文档/`。模块划分默认对应 `lib/features/<模块>`，其他结构的项目按同样规则映射自己的代码目录。
