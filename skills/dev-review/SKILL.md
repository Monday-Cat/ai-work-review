# 开发文档工作流

配合 Obsidian「AI Work Review」开发模式。需求与交付写在**同一份**开发文档里。不要在仓库里另存「需求模板 / 交付模板」。

先读项目 `AGENTS.md` 与目标模块代码；改动范围以它为准。开发文档固定写在 `docs/`，不要写进源码目录。

## 路径

- 开发文档：`docs/开发文档/<模块>/YYYY-MM-DD-<任务名>.md`
- 模块卡：`docs/开发文档/<模块>/_模块.md`（结构索引，不是任务）
- 概念卡：`docs/公用配置/<概念>.md`（公用概念的权威定义，双链目标，见「公用配置」）
- 接口文档：`docs/接口文档/<服务>/_接口.md`（外部 API 的规范化镜像，每服务一份总汇，见「接口」子命令；不在插件扫描范围，Obsidian 正常查看）
- 组件文档：`docs/组件文档/<分类>/<组件名>.md`（可复用组件的注册表，见「组件」子命令；`_索引.md` 总览）
- 模块代码：模块卡「目录」所指向的源码目录（即文档里的 **目标目录**；Flutter 默认 `lib/features/<模块>/`）
- 桥接：`.ai-review/adjustments/`
- 插件扫描 `docs/开发文档/`；旧的 `开发需求/`、`开发交付/` 仅兼容未迁移档案

`<模块>` 与一个源码模块目录 **一一对应**（Flutter 是 `lib/features/<模块>`，其他结构见「解析模块」第 1 步）。解析模块时只在 `docs/开发文档/` 下建同名文件夹。

## 公用配置（公用概念）

项目里反复出现的领域概念（如本地货币、档位、会员等级）沉淀为**概念卡**，一个概念一个文件。开发文档用双链 `[[概念名]]` 引用，概念卡是**权威定义**——AI 与代码都以它为准，改概念先改卡。

- **读**：所有读文档的命令（调整/开工/交付/整改/变更/继续）先解析文档里的 `[[概念]]` 双链，读对应概念卡再动手。**概念不明不要猜**：死链（卡不存在）或术语没链接也没定义 → 停下来问作者。
- **写**：写文档的命令（需求/调整/解析业务）里，对话或代码中的术语已有概念卡的必须加双链；反复出现但没概念卡的，提醒作者跑 `建卡`。
- **归属**：概念卡由作者定夺。AI 可代拟草稿（走 `建卡` 命令），作者确认后才落盘 `docs/公用配置/`，不要擅自发明公用概念。

## 状态

| 状态 | 谁改 | 下一步 |
|---|---|---|
| 待审核 | 技能写完需求或业务解析（流程） | 作者面板「调整」或「通过」 |
| 调整中 | 作者点「调整」，或对过代码后记「需求变更」 | `/dev-review 调整`（按新需求重新生成文档） |
| 已通过 | 作者点「通过」 | `/dev-review 开工`；需求要改 → 作者再点「调整」 |
| 开发中 | 开工时立刻改 | 做完后作者点「完结」，或先 `/dev-review 交付` |
| 已交付 | 技能填完「交付」节 | 作者点「完结」；或「缺陷」（记 BUG）/「需求变更」 |
| 完结 | 作者对开发中/已交付点「完结」 | 结束。不会再被开工。事后仍可写「缺陷」或「需求变更」 |
| 变更中 | 「调整」把变更合入文档定稿后（AI 收尾改写；漏改时作者面板点「定稿」补上） | `/dev-review 变更`：落地代码（面板主按钮「落地」＝复制该文档的变更指令；不能直接完结，避免跳过落地） |
| 整改中 | 作者写下 BUG | `/dev-review 整改` |

业务快照用 **完结**，避免误开工。

做完以后的缺陷、需求变更都写进**对应那份开发文档**，不要新开文档。开发中点「通过/完结」= **完结**，不是再变成「已通过」。状态与指令一一对应：**调整中**→`调整`（只改文档）、**变更中**→`变更`（只落地代码）、**整改中**→`整改`（只修 BUG）。对过代码以后改需求走两步：记变更 →「调整中」→ `/dev-review 调整` 合入文档定稿 →「变更中」→ `/dev-review 变更` 落地代码；变更中再记新变更，状态回到「调整中」重来这两步。「调整中」（对过代码）时面板主按钮是「定稿」：作者确认变更已合入文档后点它进入「变更中」，该状态不能直接完结，避免跳过代码落地。

## 模板：模块卡

```markdown
# 模块：<name>

- **目录**：lib/features/<name>
- **文档**：docs/开发文档/<name>
- **分层**：
- **页面**：
- **职责**：
- **业务拆解**：未拆解
- **缺陷史**：无
- **业务整合**：未整合
```

「业务拆解」只有「解析业务 / 深度拆解」会改：拆完后填 `YYYY-MM-DD（业务线1、业务线2…）`。「缺陷史」只有 `整改` 会改：每修复一条缺陷追加一行 `- YYYY-MM-DD：症状短语 → 根因短语（<任务名>）`，初值 `无`；`开工`/`变更`/`交付` 前先读它做回归。「业务整合」只有 `整合` 会改：每次整合后更新为 `YYYY-MM-DD HH:mm（n 个任务：任务名…）`，初值 `未整合`。

## 模板：组件卡

`docs/组件文档/<分类>/<组件名>.md`，一个组件一张卡；`docs/组件文档/_索引.md` 总览：

```markdown
# 组件：<名称>

- **路径**：（源码文件位置，如 lib/shared/widgets/xxx.dart）
- **分类**：（基础组件 / 业务组件）
- **标签**：#能力/xx #能力/yy #场景/zz（从 `_标签.md` 受控词表取；没有合适的先提议）
- **职责**：（什么场景用它，一句话）
- **布局**：（代码块内 ASCII 草图或「无内部布局」，画法见下方说明）
- **参数 / API**：（关键 props / 回调 / 参数表）
- **示例**：（最小用法片段）
- **不要用的场景**：（可选：边界与替代）
- **使用方**：（哪些模块 / 页面在用；以 `组件影响` 的代码反查为准，卡上的过期条目由它纠正）
```

**标签治理**（同概念卡）：`docs/组件文档/_标签.md` 是受控词表，登记两维标签的合法值——**能力**（干什么：输入 / 选择 / 倒计时 / 金额键盘 / 弹层 / 加载…）与**场景**（用在哪：表单页 / 列表行 / 深色 / 全屏…）。作者定标签；AI 打标只能从表里取，需要新标签时提议、确认后入表。词表不存在时，首次 `组件解析` 拟一版初稿请作者确认再打标。标签用 Obsidian 原生层级标签（`#能力/输入`），可全局搜索。

**布局草图**：读组件的 build / Widget 树（iOS 为布局代码），画**区域级 ASCII 草图**——代码块内用 `┌─┐│└┘` 框出大致分区与子元素位置，不抠像素。例如：

````
```
┌──────────────────┐
│ 顶部：标题 ＋ 关闭  │
│ 中部：金额输入      │
│ 底部：［确认按钮］  │
└──────────────────┘
```
````

单一控件没有内部布局的，写「无内部布局」。布局是**大致结构**示意，改了组件布局要同步重画。

## 子命令

无参数 → `状态`。

### 解析模块

1. 确定模块根并列出每个业务模块目录：优先 `lib/features/`（Flutter）；不存在则扫描项目源码的一级业务目录（iOS 按主 target 下的分组目录，Go / 小程序 / 前端按业务包或业务目录），逐个列出；歧义大时先向用户确认清单再继续。跳过 `README.md`。
2. 为每个模块确保 `docs/开发文档/<name>/` 存在（不要在源码目录里建开发文档）。
3. 按项目实际分层写或更新 `_模块.md` 的「分层」「页面」「目录」：Flutter 用 `application/data/domain/presentation`（有则写）和 `presentation/pages/*.dart`；其他结构用该项目的分层与页面惯例（如 Views / ViewModels / Services）。含「业务拆解」字段，缺则补 `未拆解`，已有日期不要覆盖。
4. 只建结构，不写业务开发文档，除非用户同时要求解析业务。

### 解析业务 <模块> [流程]

交给技能 `dev-parse-biz`。若本命令收到 `解析业务 <模块> [流程]`，按该技能执行。

### 深度拆解 [模块…] [更新]

对整个项目（或点名模块）**逐模块**解析业务，同样交给技能 `dev-parse-biz`，按其批量规则执行。

1. 先按「解析模块」刷新结构与全部 `_模块.md`（补上「业务拆解」字段）。
2. 队列：点名了模块就用点名清单；否则取全部模块，按目录名排序。
3. 增量：跳过「业务拆解」已有日期的模块；带 `更新` 或点名单个模块时强制重拆（更新既有业务文档，不重复建）。
4. 串行：一个模块的全部业务文档写完并更新其 `_模块.md` 的「业务拆解」后，才进入下一个模块。不要并行、不要同时摊开多个模块的代码。
5. 中断续跑：重跑同一命令即可，从第一个「业务拆解」仍为 `未拆解` 的模块继续。
6. 结束汇报：每模块拆出的业务线清单 + 文档路径；没拆完的如实说明停在哪，不要谎报完成。

### 建卡 \<概念\>

沉淀一个公用概念：建 `docs/公用配置/<概念>.md` 概念卡，并把项目里同一概念的不同叫法统一到规范词。

1. **定义来源**（按优先级取，拿不到就问作者，不要编）：
   - 作者在对话里直接给的说明；
   - 从代码与既有开发文档提取：全局搜该概念的相关词，定位模块后读实现，提炼「定义 / 规则」并注明来源文件；读不准的列为假设请作者确认；
   - 业务解析文档里已有现成描述的，直接引用。
2. 按模板代拟概念卡草稿（「别名」候选=搜到的变体叫法），**作者确认后**写入 `docs/公用配置/<概念>.md`。
3. **词汇统一**（只改文档，不改代码）：
   - 扫 `docs/开发文档/` 的正文章节（背景 / 需求描述 / 验收标准 / 边界），把该概念的变体词替换为规范名并加 `[[概念名]]` 双链；
   - 时间戳条目（补充需求 / 需求变更 / 缺陷记录）是历史记录，**不回改**，只保证以后新写内容用规范词；
   - 代码里命名不一致（同一概念多个标识符）时，建议作者开一份「术语统一」需求走 通过→开工 流程，不要顺手改代码。
4. 汇报：概念卡路径、别名清单、统一了哪些文档、是否建议代码重命名。

### 接口 \<摄取|变动|比对|列表\>

维护外部接口文档 `docs/接口文档/`（每服务一份总汇，模板见「模板：接口文档」）。接口命令不改业务代码。

**接口摄取 \<来源\> [服务名]**——把外部接口资料规范化成 markdown：

1. 判断来源：网页（用可用的抓取能力取正文；需登录的页面请作者另存为本地文件或粘贴）；本地文件（任意格式按扩展名解析；docx / xlsx / pdf 等二进制先用 textutil / pandoc / python 等转成文本，转不了让作者另存 txt / md）；对话粘贴。
2. 提取：端点（方法＋路径）、请求参数（名称 / 类型 / 必填 / 说明）、响应要点、认证、分组。
   - 原文没有的字段**填「暂无」**，不留空、不写「原文未提供」。
   - 接口名称 / 说明 / HTTP Method 缺失时，可从函数名、路径、参数或既有代码调用**推断**一个合理值，**逐条列给作者确认后写入**；作者不确认的填「暂无」。
   - 响应 JSON 示例一律**格式化**：```json 代码块、2 空格缩进、每个字段一行；原文截断的示例排版到可读并注明「原文截断」。散文说明用正文，不要塞进代码块。
3. 服务名缺省从文件名或域名推断，拿不准就问。
4. 写 `docs/接口文档/<服务>/_接口.md`；原始快照存同目录 `_源.<ext>`；更新 `docs/接口文档/_索引.md`（服务、快照日期、接口数、来源，双链到各 `_接口.md`）。
5. 汇报：接口数、分组、存疑字段清单。

**接口变动 \<服务\>**——检测对方接口变化：

1. 按 `_接口.md` 的「来源 / 获取方式」重新获取；拿不到（链接失效 / 文件没更新）就问作者要新资料，不要用旧源猜。
2. 用与摄取相同的规则重新规范化（临时，不落盘），与现有 `_接口.md` 逐接口比对，产出**变动清单**：新增 / 删除 / 变更接口，变更给字段级明细（参数增删、类型、必填、路径、说明）。
3. 更新 `_接口.md`（正文＋快照日期＋「变更历史」追加一行 `- YYYY-MM-DD HH:mm：新增 x、删除 y、变更 z`），覆盖 `_源`，刷新 `_索引.md`。
4. **问作者是否生成适配需求**：确认后在 `docs/开发文档/<相关模块>/` 按 `需求` 建「<服务>接口变动-<日期>」文档（状态待审核），变动明细写进需求描述与验收标准；受影响的旧文档提示作者记「需求变更」。作者不确认就不碰开发文档。

**接口比对 \<服务\> [模块]**——接口文档对照代码与开发文档，找漂移：

1. 读 `_接口.md`；无模块参数则扫全项目调用点（Flutter：`*_api_repository.dart` 的 path 常量与参数 map；iOS：API 宏清单＋VM 调用；其他结构按网络层惯例），点名模块则只扫该模块；同时对照 `docs/开发文档/` 里描述的接口。
2. 报告三类不一致：**文档有、代码未用**（漏实现或已废弃）／**代码在用、文档没有**（文档缺失，建议向后端确认）／**同名接口参数或路径不一致**（实现漂移，风险最高）。
3. 只报告不改代码；要修的走 `需求`（补实现）/ `变更`（改实现）。

**接口列表**：扫描 `docs/接口文档/`，刷新 `_索引.md` 并向作者展示。

### 组件 \<解析|查|登记|影响\>

维护组件注册表 `docs/组件文档/`：让 AI 写 UI 前知道已有什么可复用，不重复造轮子。组件命令不直接改业务代码。

**组件解析 [模块]**——扫描建库：

1. 范围：点名模块只扫它的组件目录（Flutter `presentation/widgets/`；iOS 为 View 目录）；无参数 = 全部模块＋公共组件区（Flutter `lib/shared/widgets/` 与 `lib/foundation/`；外部 UI 包只记卡不展开）。逐模块串行，上下文纪律同「深度拆解」。
2. 每个可复用组件按「模板：组件卡」建卡（标签、布局草图、职责、参数 / API、最小示例、使用方）；一次性的私有小 widget 不入册——只收职责明确、可当词用的。打标签从 `_标签.md` 受控词表取，词表不存在先拟初稿请作者确认。
3. **发现功能雷同的组件**（不同模块各写了一份相似的东西）：不直接重构，生成「组件抽取」需求文档到对应模块（状态 `待审核`，走审核-开工流程）：写明雷同清单、建议的公共组件设计、迁移范围。
4. `_索引.md` **按能力标签分组**（组内每行：组件、路径、场景标签、职责短语），汇报：新入册 n 个、重复嫌疑 k 组。

**组件查 \<需求描述\>**——选取推荐，**标签优先**：从需求描述提取能力 / 场景关键词 → 按标签（`#能力/…` `#场景/…`）命中缩小候选 → 读候选卡的职责与示例定夺 → 给推荐＋最小用法。没有合适的就直说没有，问作者是否新建（新建的可复用组件交付时 `组件登记`）。也可提示作者在 Obsidian 全局搜 `#能力/xx` 人工定位。

**组件登记 \<路径\>**——入库：给指定组件文件按模板补卡（**打标必须从 `_标签.md` 词表取，缺的提议**；补**布局 ASCII 草图**，组件被改后重画）＋更新索引。组件被修改后重跑一次即可刷新卡（布局 / 参数 / 示例 / 使用方）。

**组件影响 \<组件名 | 页面名 | 路径\>**——**反向映射**：改组件或页面前反查谁在用它（业务→页面→组件 影响链的反向走法）。

1. 定位目标：按名查组件卡取「路径」，或直接给路径；给页面名则定位页面类文件。
2. **代码反查为准**：全项目搜该组件 / 页面的引用（Flutter：类名 / 构造调用；iOS：类引用），组件卡「使用方」做交叉核对——代码里有、卡上没有的补进卡；卡上有、代码里没了的标废弃。
3. 输出**影响清单**：受影响页面 / 组件 / 模块 → 提及它们的业务文档（grep `[[页面]]` / `[[组件]]` 双链命中）→ 各模块「缺陷史」相关条目（每个使用方都要回归，有缺陷史的重点盯）。
4. 建议生成「组件 / 页面变更」需求文档（状态 `待审核`）：影响清单写进**边界**（明确波及面）与**验收标准**（每个使用方一条验收点）。
5. 变更落地交付后：重跑 `组件登记` 刷新卡，跑 `整合` 把行为变化并回各使用方的业务文档。

反向映射的另一路是 Obsidian 原生反链：需求 / 任务文档里的 `优先复用：[[组件名]]` 双链、业务文档里的 `[[页面名]]`，会在组件卡与页面的**反向链接面板**里全部可见。

### 需求 \<任务描述\>

1. 推断模块与目标目录；不确定先问。
2. 按模板新建 `docs/开发文档/<模块>/今天日期-任务名.md`；**状态一律 `待审核`**——即使作者说马上开工也不要写成 开发中/完结，改代码只能由 `开工` 命令触发；来源 `对话`；**目标目录** 填代码路径。对话里的术语已有概念卡的，用 `[[概念名]]` 双链引用（见「公用配置」）。
3. 告诉作者去面板点「调整」或「通过」。不要开工。涉及 UI 的需求，用 `组件查` 标注「优先复用：[[组件名]]」（没有合适的如实写新建）；要修改共享组件的，先跑 `组件影响`，把受影响方写进边界与验收；修改既有业务的需求，从对应业务文档的页面 / 组件双链清单取受影响面写进边界。

### 调整

处理所有状态为「调整中」的开发文档（兼容旧「调整」；含 adjustments、「补充需求」与「需求变更」未落实条目）：按作者的新需求**重新生成这份需求文档**——把意见合并进需求描述/验收标准/边界。**只改文档，不改业务代码。** 清理已处理 adjustments。

完成后按文档阶段改状态：

- **需求阶段**（交付节仍空）→ `待审核`，等作者重新「通过」。
- **对过代码**（交付节有实质内容，或「需求变更」有未落实条目）→ `变更中`，等 `/dev-review 变更` 落地代码。漏改时作者可在面板点「定稿」补上。

没有「调整中」文档、但 adjustments/ 里挂着待处理意见时，按意见所在文档的状态**直接分流，不要停下来问、也不要空转**：

- 状态「变更中」→ 文档已定稿，直接按 `变更` 落地代码。
- 状态不是「调整中」但「需求变更」有未落实条目 → 先按本命令把变更合入文档（→`变更中`），接着按 `变更` 落地。
- 状态「整改中」或「缺陷记录」里有未整改条目 → 直接按 `整改` 处理（那是 BUG，不属于调整）。
- 交付节已有实质内容的旧档（历史「交付调整」）→ 按 `继续`。
- 全都没有 → 如实说没有待处理意见，等作者在面板点按钮。

### 开工

对状态 `已通过` 且尚未开发中/已交付/完结/整改中/变更中的文档：立刻改 `开发中`，按验收改 **目标目录** 里的代码。不要改未通过的文档，也不要动已经完结的文档。动代码前先读该模块 `_模块.md` 的「缺陷史」（没有就扫该模块各文档 `## 缺陷记录` 已填「整改」的条目）作回归清单：避开已知坑，改完逐条自查没把旧缺陷重新弄坏。文档里的 `[[概念]]` 双链先解析、读对应概念卡（见「公用配置」），以卡为准；没链接的概念不猜、问作者。写 UI 代码前先查 `docs/组件文档/`（或跑 `组件查`），优先复用已有组件；确需新建的可复用组件，交付时用 `组件登记` 入库。改动波及共享组件时，先跑 `组件影响` 反查全部使用方，改完逐一回归。

### 交付 \<路径或任务名\>

对照验收填同一文档的「交付」节；**交付日期** 填今天；状态 `已交付`。不要另建交付文件。「自测结果」里写明对照该模块「缺陷史」的回归检查（至少覆盖本次改动触及页面的旧缺陷）。本次交付了新的可复用组件时，用 `组件登记` 入库。交付后提醒作者：该模块的改动之后用 `整合` 并回业务文档（`状态` 命令可见欠账）。

### 整改 [模块或文档]

作者已经把 BUG 写进对应开发文档时用。**不要替作者编写/编译一份 BUG 文档。**只针对 BUG（交付结果与验收不符）；需求要改：未开工走 `调整`，已过代码走 `变更`。

1. 打开指定文档，或该模块下带未处理缺陷的开发文档（看 `## 缺陷记录` 里还没有填「整改」的条目；状态「整改中」优先）。顺带读该模块 `_模块.md` 的「缺陷史」：症状与旧条相同就是复发。
2. 找不到已有文档就问，不要新建。
3. 若其实是新功能，改走 `需求`。
4. 只读与这些缺陷相关的少量代码并改。不要解析整个模块、不要重填交付表、不要走待审核。
5. 在同一条目补上 `- **整改**：`（改了什么）和 `- **根因**：`（为什么会坏、同类代码要避开的点，一两句），状态改回 `完结`。清理已处理的 adjustments JSON。
6. 把每条修复汇入模块卡 `_模块.md` 的「缺陷史」：追加一行 `- YYYY-MM-DD：症状短语 → 根因短语（<任务名>）`；模块卡不存在就按「模板：模块卡」新建（只填 目录/文档/缺陷史）。复发时在「整改」行末注明 `复发自 <旧条日期>`。

`添加BUG` 是本命令的别名，行为相同：读文档里已有的缺陷，不要再写一套。

### 变更 [模块或文档]

处理状态「变更中」的开发文档：变更已由 `调整` 合入文档并定稿，这里只做**代码落地**。**不要新开需求文档。**

1. 读文档的需求描述/验收标准（已含变更）、`## 需求变更` 里尚未落实的条目，与该模块 `_模块.md` 的「缺陷史」作回归清单；若文档还在「调整中」，先按 `调整` 定稿再落地。
2. 按文档调整**目标目录**里的代码，完成变更落地（已开工或已完结都直接改，不要再走待审核）。落地后对照缺陷史逐条自查。
3. 在同一条目补上 `- **落实**：`（写了什么）。若原来是开发中则改回 `开发中`，若原来是完结则改回 `完结`。

### 整合 [模块]

把已完结任务的改动**增量并回业务文档**，消除「业务文档过期」。业务文档（`解析业务` / `深度拆解` 的产物）是模块现状的真相，任务文档是过程历史。

1. 范围：点名模块只整合它；无参数则列出所有有未整合任务的模块，与作者确认后逐个做。
2. 收集增量：该模块下状态为 完结 / 已交付、且「基本信息」里没有 `- **已整合**：` 标记的任务文档；取其需求、交付内容、缺陷根因。
3. 合并：把每个任务的改动按目标目录与业务名匹配到对应业务线文档，**原地更新**受影响章节（主流程 / 业务规则 / 分支异常 / 数据依赖）；行为有变但业务文档没有对应章节的，在合适的业务线文档补一节。同时维护业务文档的页面 / 组件双链清单（新页面入链、废弃页移除）。**整合不了或与现状矛盾的列入待人工确认清单，不要硬改。**
4. 盖戳：被整合的任务文档「基本信息」加一行 `- **已整合**：YYYY-MM-DD HH:mm`；`_模块.md` 的「业务整合」更新为 `YYYY-MM-DD HH:mm（n 个任务：任务名…）`。
5. 该模块「业务拆解」仍为 `未拆解`：提示先跑 `解析业务`，本次跳过。
6. 汇报：每模块更新了哪些业务文档、待确认清单、矛盾较多建议 `深度拆解 <模块> 更新` 重拆的模块。

与 `深度拆解` 的分工：整合用任务文档的意图做增量（便宜、快）；`深度拆解 <模块> 更新` 从代码重parse（事实基准）。业务文档与代码矛盾多时用后者。

### 继续

落实已交付文档上的调整意见（代码 + 交付节）。完成后状态改回 `已交付`，请作者再审。

### 状态

扫描 `docs/开发文档/`（及旧 `开发需求/`、`开发交付/`），按模块文件夹分组，指出下一步该谁；同时标出各模块的**未整合任务数**（已完结但没有「已整合」标记的任务）——业务文档的欠账。

## 纪律

- 模板只存在本技能内。
- 开发文档只写 `docs/开发文档/<模块>/`，不写进 `lib/`。
- 「开工」只处理「已通过」，不要改「完结」或作者没点名的文档。
- 状态与指令一一对应：「调整中」→`调整`（只改文档），「变更中」→`变更`（只落地代码）；「开工」才第一次改代码。
- 「变更」/「整改」不新写文档：作者把内容写在对应开发文档里，技能只读并改。
- 缺陷只针对 BUG，走「整改」，和「调整」「变更」分开。
- 修复过的缺陷是模块资产：`整改` 必补「根因」并更新模块卡「缺陷史」；`开工`/`变更`/`交付` 必读缺陷史防复发。
- 公用概念以 `docs/公用配置/` 概念卡为准：读文档先解双链、写文档要加双链；概念不明不猜、问作者；概念卡由作者定夺，AI 只代拟草稿。
- 接口文档是外部事实的镜像：正文只由 `接口摄取` / `接口变动` 维护（作者不手改正文，「变更历史」除外）；接口变动要改代码时走 `需求` / `变更`，接口命令不动业务代码。
- 业务文档的时效靠 `整合` 维护：交付/完结攒下的改动由 `整合` 并回业务文档；矛盾列待确认，不硬改。
- 组件文档是复用资产：`开工` 写 UI 前必查、优先复用不重复造轮子；功能雷同的抽取只生成需求走流程；组件文档由 `组件解析` / `组件登记` 维护，标签从受控词表取、新标签提议经作者确认。
- 测试结果如实写。
- `_模块.md` 不是任务，不要改它的状态、不要开工它。
