# 开发文档工作流

配合 Obsidian「AI Work Review」开发模式。需求与交付写在**同一份**开发文档里。不要在仓库里另存「需求模板 / 交付模板」。

先读项目 `AGENTS.md` 与目标模块代码；改动范围以它为准。开发文档固定写在 `docs/`，不要写进源码目录。

## 路径

- 开发文档：`docs/开发文档/<模块>/YYYY-MM-DD-<任务名>.md`
- 模块卡：`docs/开发文档/<模块>/_模块.md`（结构索引，不是任务）
- 概念卡：`docs/公用配置/<概念>.md`（公用概念的权威定义，双链目标，见「公用配置」）
- 模块代码：模块卡「目录」所指向的源码目录（即文档里的 **目标目录**；Flutter 默认 `lib/features/<模块>/`）
- 桥接：`.ai-review/adjustments/`
- 插件扫描 `docs/开发文档/`；旧的 `开发需求/`、`开发交付/` 仅兼容未迁移档案

`<模块>` 与一个源码模块目录 **一一对应**（Flutter 是 `lib/features/<模块>`，其他结构见「解析模块」第 1 步）。解析模块时只在 `docs/开发文档/` 下建同名文件夹。

## 公用配置（公用概念）

项目里反复出现的领域概念（如本地货币、档位、会员等级）沉淀为**概念卡**，一个概念一个文件。开发文档用双链 `[[概念名]]` 引用，概念卡是**权威定义**——AI 与代码都以它为准，改概念先改卡。

- **读**：所有读文档的命令（调整/开工/交付/整改/变更/继续）先解析文档里的 `[[概念]]` 双链，读对应概念卡再动手。**概念不明不要猜**：死链（卡不存在）或术语没链接也没定义 → 停下来问作者。
- **写**：写文档的命令（需求/调整/解析业务）里，对话或代码中的术语已有概念卡的必须加双链；反复出现但没概念卡的，提醒作者跑 `建卡`。
- **归属**：概念卡由作者定夺。AI 可代拟草稿（走 `建卡` 命令），作者确认后才落盘 `docs/公用配置/`，不要擅自发明公用概念。

## 状态

| 状态 | 谁改 | 下一步 |
|---|---|---|
| 待审核 | 技能写完需求或业务解析（流程） | 作者面板「调整」或「通过」 |
| 调整中 | 作者点「调整」，或对过代码后记「需求变更」 | `/dev-review 调整`（按新需求重新生成文档） |
| 已通过 | 作者点「通过」 | `/dev-review 开工`；需求要改 → 作者再点「调整」 |
| 开发中 | 开工时立刻改 | 做完后作者点「完结」，或先 `/dev-review 交付` |
| 已交付 | 技能填完「交付」节 | 作者点「完结」；或「缺陷」（记 BUG）/「需求变更」 |
| 完结 | 作者对开发中/已交付点「完结」 | 结束。不会再被开工。事后仍可写「缺陷」或「需求变更」 |
| 变更中 | 「调整」把变更合入文档定稿后（AI 收尾改写；漏改时作者面板点「定稿」补上） | `/dev-review 变更`：落地代码（面板主按钮「落地」＝复制该文档的变更指令；不能直接完结，避免跳过落地） |
| 整改中 | 作者写下 BUG | `/dev-review 整改` |

业务快照用 **完结**，避免误开工。

做完以后的缺陷、需求变更都写进**对应那份开发文档**，不要新开文档。开发中点「通过/完结」= **完结**，不是再变成「已通过」。状态与指令一一对应：**调整中**→`调整`（只改文档）、**变更中**→`变更`（只落地代码）、**整改中**→`整改`（只修 BUG）。对过代码以后改需求走两步：记变更 →「调整中」→ `/dev-review 调整` 合入文档定稿 →「变更中」→ `/dev-review 变更` 落地代码；变更中再记新变更，状态回到「调整中」重来这两步。「调整中」（对过代码）时面板主按钮是「定稿」：作者确认变更已合入文档后点它进入「变更中」，该状态不能直接完结，避免跳过代码落地。

## 模板：模块卡

```markdown
# 模块：<name>

- **目录**：lib/features/<name>
- **文档**：docs/开发文档/<name>
- **分层**：
- **页面**：
- **职责**：
- **业务拆解**：未拆解
- **缺陷史**：无
```

「业务拆解」只有「解析业务 / 深度拆解」会改：拆完后填 `YYYY-MM-DD（业务线1、业务线2…）`。「缺陷史」只有 `整改` 会改：每修复一条缺陷追加一行 `- YYYY-MM-DD：症状短语 → 根因短语（<任务名>）`，初值 `无`；`开工`/`变更`/`交付` 前先读它做回归。

## 模板：概念卡

`docs/公用配置/<概念名>.md`，一个概念一个文件：

```markdown
# 概念：<名称>

- **定义**：（一句话：它是什么、边界在哪）
- **规则**：（与它相关的硬规则，分条）
- **别名**：（可选：文档里出现这些词也指本概念）
```

## 子命令

无参数 → `状态`。

### 解析模块

1. 确定模块根并列出每个业务模块目录：优先 `lib/features/`（Flutter）；不存在则扫描项目源码的一级业务目录（iOS 按主 target 下的分组目录，Go / 小程序 / 前端按业务包或业务目录），逐个列出；歧义大时先向用户确认清单再继续。跳过 `README.md`。
2. 为每个模块确保 `docs/开发文档/<name>/` 存在（不要在源码目录里建开发文档）。
3. 按项目实际分层写或更新 `_模块.md` 的「分层」「页面」「目录」：Flutter 用 `application/data/domain/presentation`（有则写）和 `presentation/pages/*.dart`；其他结构用该项目的分层与页面惯例（如 Views / ViewModels / Services）。含「业务拆解」字段，缺则补 `未拆解`，已有日期不要覆盖。
4. 只建结构，不写业务开发文档，除非用户同时要求解析业务。

### 解析业务 <模块> [流程]

交给技能 `dev-parse-biz`。若本命令收到 `解析业务 <模块> [流程]`，按该技能执行。

### 深度拆解 [模块…] [更新]

对整个项目（或点名模块）**逐模块**解析业务，同样交给技能 `dev-parse-biz`，按其批量规则执行。

1. 先按「解析模块」刷新结构与全部 `_模块.md`（补上「业务拆解」字段）。
2. 队列：点名了模块就用点名清单；否则取全部模块，按目录名排序。
3. 增量：跳过「业务拆解」已有日期的模块；带 `更新` 或点名单个模块时强制重拆（更新既有业务文档，不重复建）。
4. 串行：一个模块的全部业务文档写完并更新其 `_模块.md` 的「业务拆解」后，才进入下一个模块。不要并行、不要同时摊开多个模块的代码。
5. 中断续跑：重跑同一命令即可，从第一个「业务拆解」仍为 `未拆解` 的模块继续。
6. 结束汇报：每模块拆出的业务线清单 + 文档路径；没拆完的如实说明停在哪，不要谎报完成。

### 建卡 \<概念\>

沉淀一个公用概念：建 `docs/公用配置/<概念>.md` 概念卡，并把项目里同一概念的不同叫法统一到规范词。

1. **定义来源**（按优先级取，拿不到就问作者，不要编）：
   - 作者在对话里直接给的说明；
   - 从代码与既有开发文档提取：全局搜该概念的相关词，定位模块后读实现，提炼「定义 / 规则」并注明来源文件；读不准的列为假设请作者确认；
   - 业务解析文档里已有现成描述的，直接引用。
2. 按模板代拟概念卡草稿（「别名」候选=搜到的变体叫法），**作者确认后**写入 `docs/公用配置/<概念>.md`。
3. **词汇统一**（只改文档，不改代码）：
   - 扫 `docs/开发文档/` 的正文章节（背景 / 需求描述 / 验收标准 / 边界），把该概念的变体词替换为规范名并加 `[[概念名]]` 双链；
   - 时间戳条目（补充需求 / 需求变更 / 缺陷记录）是历史记录，**不回改**，只保证以后新写内容用规范词；
   - 代码里命名不一致（同一概念多个标识符）时，建议作者开一份「术语统一」需求走 通过→开工 流程，不要顺手改代码。
4. 汇报：概念卡路径、别名清单、统一了哪些文档、是否建议代码重命名。

### 需求 \<任务描述\>

1. 推断模块与目标目录；不确定先问。
2. 按模板新建 `docs/开发文档/<模块>/今天日期-任务名.md`；**状态一律 `待审核`**——即使作者说马上开工也不要写成 开发中/完结，改代码只能由 `开工` 命令触发；来源 `对话`；**目标目录** 填代码路径。对话里的术语已有概念卡的，用 `[[概念名]]` 双链引用（见「公用配置」）。
3. 告诉作者去面板点「调整」或「通过」。不要开工。

### 调整

处理所有状态为「调整中」的开发文档（兼容旧「调整」；含 adjustments、「补充需求」与「需求变更」未落实条目）：按作者的新需求**重新生成这份需求文档**——把意见合并进需求描述/验收标准/边界。**只改文档，不改业务代码。** 清理已处理 adjustments。

完成后按文档阶段改状态：

- **需求阶段**（交付节仍空）→ `待审核`，等作者重新「通过」。
- **对过代码**（交付节有实质内容，或「需求变更」有未落实条目）→ `变更中`，等 `/dev-review 变更` 落地代码。漏改时作者可在面板点「定稿」补上。

没有「调整中」文档、但 adjustments/ 里挂着待处理意见时，按意见所在文档的状态**直接分流，不要停下来问、也不要空转**：

- 状态「变更中」→ 文档已定稿，直接按 `变更` 落地代码。
- 状态不是「调整中」但「需求变更」有未落实条目 → 先按本命令把变更合入文档（→`变更中`），接着按 `变更` 落地。
- 状态「整改中」或「缺陷记录」里有未整改条目 → 直接按 `整改` 处理（那是 BUG，不属于调整）。
- 交付节已有实质内容的旧档（历史「交付调整」）→ 按 `继续`。
- 全都没有 → 如实说没有待处理意见，等作者在面板点按钮。

### 开工

对状态 `已通过` 且尚未开发中/已交付/完结/整改中/变更中的文档：立刻改 `开发中`，按验收改 **目标目录** 里的代码。不要改未通过的文档，也不要动已经完结的文档。动代码前先读该模块 `_模块.md` 的「缺陷史」（没有就扫该模块各文档 `## 缺陷记录` 已填「整改」的条目）作回归清单：避开已知坑，改完逐条自查没把旧缺陷重新弄坏。文档里的 `[[概念]]` 双链先解析、读对应概念卡（见「公用配置」），以卡为准；没链接的概念不猜、问作者。

### 交付 \<路径或任务名\>

对照验收填同一文档的「交付」节；**交付日期** 填今天；状态 `已交付`。不要另建交付文件。「自测结果」里写明对照该模块「缺陷史」的回归检查（至少覆盖本次改动触及页面的旧缺陷）。

### 整改 [模块或文档]

作者已经把 BUG 写进对应开发文档时用。**不要替作者编写/编译一份 BUG 文档。**只针对 BUG（交付结果与验收不符）；需求要改：未开工走 `调整`，已过代码走 `变更`。

1. 打开指定文档，或该模块下带未处理缺陷的开发文档（看 `## 缺陷记录` 里还没有填「整改」的条目；状态「整改中」优先）。顺带读该模块 `_模块.md` 的「缺陷史」：症状与旧条相同就是复发。
2. 找不到已有文档就问，不要新建。
3. 若其实是新功能，改走 `需求`。
4. 只读与这些缺陷相关的少量代码并改。不要解析整个模块、不要重填交付表、不要走待审核。
5. 在同一条目补上 `- **整改**：`（改了什么）和 `- **根因**：`（为什么会坏、同类代码要避开的点，一两句），状态改回 `完结`。清理已处理的 adjustments JSON。
6. 把每条修复汇入模块卡 `_模块.md` 的「缺陷史」：追加一行 `- YYYY-MM-DD：症状短语 → 根因短语（<任务名>）`；模块卡不存在就按「模板：模块卡」新建（只填 目录/文档/缺陷史）。复发时在「整改」行末注明 `复发自 <旧条日期>`。

`添加BUG` 是本命令的别名，行为相同：读文档里已有的缺陷，不要再写一套。

### 变更 [模块或文档]

处理状态「变更中」的开发文档：变更已由 `调整` 合入文档并定稿，这里只做**代码落地**。**不要新开需求文档。**

1. 读文档的需求描述/验收标准（已含变更）、`## 需求变更` 里尚未落实的条目，与该模块 `_模块.md` 的「缺陷史」作回归清单；若文档还在「调整中」，先按 `调整` 定稿再落地。
2. 按文档调整**目标目录**里的代码，完成变更落地（已开工或已完结都直接改，不要再走待审核）。落地后对照缺陷史逐条自查。
3. 在同一条目补上 `- **落实**：`（写了什么）。若原来是开发中则改回 `开发中`，若原来是完结则改回 `完结`。

### 继续

落实已交付文档上的调整意见（代码 + 交付节）。完成后状态改回 `已交付`，请作者再审。

### 状态

扫描 `docs/开发文档/`（及旧 `开发需求/`、`开发交付/`），按模块文件夹分组，指出下一步该谁。

## 纪律

- 模板只存在本技能内。
- 开发文档只写 `docs/开发文档/<模块>/`，不写进 `lib/`。
- 「开工」只处理「已通过」，不要改「完结」或作者没点名的文档。
- 状态与指令一一对应：「调整中」→`调整`（只改文档），「变更中」→`变更`（只落地代码）；「开工」才第一次改代码。
- 「变更」/「整改」不新写文档：作者把内容写在对应开发文档里，技能只读并改。
- 缺陷只针对 BUG，走「整改」，和「调整」「变更」分开。
- 修复过的缺陷是模块资产：`整改` 必补「根因」并更新模块卡「缺陷史」；`开工`/`变更`/`交付` 必读缺陷史防复发。
- 公用概念以 `docs/公用配置/` 概念卡为准：读文档先解双链、写文档要加双链；概念不明不猜、问作者；概念卡由作者定夺，AI 只代拟草稿。
- 测试结果如实写。
- `_模块.md` 不是任务，不要改它的状态、不要开工它。
