# 开发交付审核（dev-review）

你负责开发任务的三个环节：**开工前转写需求档案**、**完工后写交付单**、**按作者审核意见继续开发**。作者在 Obsidian（AI 工作审核插件）里审阅需求与交付单，用「调整」写不足点；你据其继续迭代，直到作者标记通过。

## 路径约定

- 审核 vault：`<工作区根>/小说/`（若存在 `<工作区根>/.zcode/dev-review.json`，以其 `vault` 字段为准）。
- 需求档案：`<vault>/开发需求/YYYY-MM-DD-<任务名>.md`（模板：`开发需求/需求模板.md`）
- 交付单：`<vault>/开发交付/YYYY-MM-DD-<任务名>.md`（模板：`开发交付/交付模板.md`）
- 桥接目录：`<vault>/.ai-review/`（插件管理，不要手工归档）
- 模板文件本身（需求模板.md/交付模板.md）不要修改、不要当数据读写。

## 命令

### `/dev-review 需求 <任务描述>`

开工前调用，把对话中的需求固化为需求档案：

1. 按模板新建 `开发需求/YYYY-MM-DD-<任务名>.md`，填齐：背景与目标、需求描述（分条）、**验收标准（可验证的 checkbox）**、边界与非目标。状态置 `待开发`。
2. 描述含糊时先向作者确认关键歧义再落档；作者已说清的部分不要反复追问。
3. 档案落盘后即可开始开发；后续交付单必须链接这份档案。

### `/dev-review 交付 <需求文档路径或任务名>`

功能完成后调用，产出交付单供作者审核：

1. 找到对应需求档案（按路径或按任务名匹配 `开发需求/` 下文件）。
2. 逐条对照验收标准，检查实现是否完整；有缺口先补齐或如实写明未达成。
3. 按模板新建 `开发交付/YYYY-MM-DD-<任务名>.md`：
   - **状态**：`待审核`
   - **完成内容**：改动文件清单（文件 + 一句话说明改了什么、为什么）
   - **自测结果**：实际执行的命令/测试与结果摘要；没跑的要写明原因，不得编造通过
   - **验收步骤**：作者如何人工验证
   - **风险与遗留**：已知问题、后续事项
4. 同步把需求档案状态改为 `已交付`，并在其「关联交付」回填交付单链接。
5. 结束时告诉作者：交付单路径 + 打开 Obsidian 审核面板查看，可点「调整」写意见或在交付单「审核意见」节直接写。

### `/dev-review 继续`

作者说"审完了/你继续"时调用，读取审核结果并落实：

1. 收集意见，两个来源都查：
   - 桥接目录 `adjustments/` 下的 JSON（插件「调整」产生，`note` 字段为意见原文）；
   - `开发交付/` 各交付单的「审核意见」节（有实质内容且未标记"已处理"的）与「状态」字段。
2. 若某交付单状态为 `已通过` 且无未处理意见 → 跳过，不画蛇添足。
3. 逐条落实意见：改代码、跑测试、更新文档。**涉及小说 vault 内文档的修改走插件 proposals 流程**（整份新内容写入 `.ai-review/proposals/<镜像路径>.md`，由作者 diff 确认）；交付单与需求档案本身可直接改。
4. 全部落实后：更新交付单——状态改回 `待审核`、完成内容追加本轮修改记录、把「审核意见」节已处理的条目标注 `（已处理）`；删除已处理的 `adjustments/*.json`。
5. 汇总回复：处理了哪些意见、改了什么、测试结果；请作者复审。

### `/dev-review 状态`

列出当前所有任务状态：遍历 `开发需求/` 与 `开发交付/`，按任务汇总（需求状态、交付单状态、未处理意见数），指出卡在哪一步、下一步该谁动作。

## 纪律

- 需求与交付单必须诚实：测试没过就写没过，未实现就写未实现；作者靠交付单做批准决策。
- 意见处理宁多勿漏：不确定作者意图时按保守方向执行并在汇总里说明假设。
- 不修改 `开发需求/`、`开发交付/` 之外的 vault 内容（小说设定文件一律走 proposals，由作者确认）。
- 每次交付/继续后，交付单的状态字段必须与实际一致（待审核/修改中/已通过），插件靠它跟踪。
