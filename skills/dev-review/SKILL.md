# 开发文档工作流

配合 Obsidian「AI Work Review」开发模式。需求与交付写在**同一份**开发文档里。不要在仓库里另存「需求模板 / 交付模板」。

先读项目 `AGENTS.md` 与目标模块代码；改动范围以它为准。开发文档固定写在 `docs/`，不要写进源码目录。

## 路径

- 开发文档：`docs/开发文档/<模块>/YYYY-MM-DD-<任务名>.md`
- 模块卡：`docs/开发文档/<模块>/_模块.md`（结构索引，不是任务）
- 概念卡：`docs/公用配置/<概念>.md`（公用概念的权威定义，双链目标，见「公用配置」）
- 接口文档：`docs/接口文档/<服务>/_接口.md`（外部 API 的规范化镜像，每服务一份总汇，见「接口」子命令；不在插件扫描范围，Obsidian 正常查看）
- 组件文档：`docs/组件文档/<分类>/<组件名>.md`（可复用组件的注册表，见「组件」子命令；`_索引.md` 总览）
- 页面文档：`docs/页面文档/<模块>/<页面名>.md`（页面布局索引：编号槽位草图＋四要素图例，画法见 `references/components.md`；`_索引.md` 总览）
- 模块代码：模块卡「目录」所指向的源码目录（即文档里的 **目标目录**；Flutter 默认 `lib/features/<模块>/`）
- 桥接：`.ai-review/adjustments/`
- 插件扫描 `docs/开发文档/`；旧的 `开发需求/`、`开发交付/` 仅兼容未迁移档案

`<模块>` 与一个源码模块目录 **一一对应**（Flutter 是 `lib/features/<模块>`，其他结构见「解析模块」第 1 步）。解析模块时只在 `docs/开发文档/` 下建同名文件夹。

**参考文件**：`references/`（`templates` 文档模板 / `interface` 接口命令 / `components` 组件与页面卡＋布局草图标记 / `doc-check` 文档检查）是模板与子命令细则的正本，SKILL.md 只留核心与路由——跑子命令前按路由先读对应文件；改细则改参考文件本体，不要在 SKILL.md 复述。

## 公用配置（公用概念）

项目里反复出现的领域概念（如本地货币、档位、会员等级）沉淀为**概念卡**，一个概念一个文件。开发文档用双链 `[[概念名]]` 引用，概念卡是**权威定义**——AI 与代码都以它为准，改概念先改卡。

- **读**：所有读文档的命令（调整/开工/交付/整改/变更/继续）先解析文档里的 `[[概念]]` 双链，读对应概念卡再动手。**概念不明不要猜**：死链（卡不存在）或术语没链接也没定义 → 停下来问作者。
- **写**：写文档的命令（需求/微改/调整/添加/解析业务）里，对话或代码中的术语已有概念卡的必须加双链；反复出现但没概念卡的，提醒作者跑 `建卡`。
- **归属**：概念卡由作者定夺。AI 可代拟草稿（走 `建卡` 命令），作者确认后才落盘 `docs/公用配置/`，不要擅自发明公用概念。

## 状态

| 状态 | 谁改 | 下一步 |
|---|---|---|
| 待审核 | 技能写完需求或业务解析（流程） | 作者面板「调整」或「通过」 |
| 调整中 | 作者点「调整」，或经面板 / `添加` 记「需求变更」「补充需求」 | `/dev-review 调整`（按新需求重新生成文档） |
| 已通过 | 作者点「通过」 | `/dev-review 开工`；需求要改 → 作者再点「调整」 |
| 开发中 | 开工时立刻改 | 做完后作者点「完结」，或先 `/dev-review 交付` |
| 已交付 | 技能填完「交付」节 | 作者点「完结」；或「缺陷」（记 BUG）/「需求变更」 |
| 完结 | 作者对开发中/已交付点「完结」 | 结束。不会再被开工。事后仍可写「缺陷」或「需求变更」 |
| 变更中 | 「调整」把变更合入文档定稿后（AI 收尾改写；漏改时作者面板点「定稿」补上） | `/dev-review 变更`：落地代码（面板主按钮「落地」＝复制该文档的变更指令；不能直接完结，避免跳过落地） |
| 整改中 | 作者点「缺陷」或 `添加 BUG` 记下 BUG | `/dev-review 整改` |

业务快照用 **完结**，避免误开工。

做完以后的缺陷、需求变更都写进**对应那份开发文档**，不要新开文档。开发中点「通过/完结」= **完结**，不是再变成「已通过」。状态与指令一一对应：**调整中**→`调整`（只改文档）、**变更中**→`变更`（只落地代码）、**整改中**→`整改`（只修 BUG）。**记录与处理分离**：BUG、需求变更、补充需求由作者经面板按钮或 `添加` 落笔，处理指令只认文档里已记录的条目——没有记录就如实说明并停，不替作者编记录、不代跑其他指令。对过代码以后改需求走两步：记变更 →「调整中」→ `/dev-review 调整` 合入文档定稿 →「变更中」→ `/dev-review 变更` 落地代码；变更中再记新变更，状态回到「调整中」重来这两步。「调整中」（对过代码）时面板主按钮是「定稿」：作者确认变更已合入文档后点它进入「变更中」，该状态不能直接完结，避免跳过代码落地。「变更」遇到还在「调整中」的文档要停下等定稿，不要自己串跑「调整」。

## 子命令

无参数 → `状态`。

### 解析模块

1. 确定模块根并列出每个业务模块目录：优先 `lib/features/`（Flutter）；不存在则扫描项目源码的一级业务目录（iOS 按主 target 下的分组目录，Go / 小程序 / 前端按业务包或业务目录），逐个列出；歧义大时先向用户确认清单再继续。跳过 `README.md`。
2. 为每个模块确保 `docs/开发文档/<name>/` 存在（不要在源码目录里建开发文档）。
3. 按项目实际分层写或更新 `_模块.md` 的「分层」「页面」「目录」：Flutter 用 `application/data/domain/presentation`（有则写）和 `presentation/pages/*.dart`；其他结构用该项目的分层与页面惯例（如 Views / ViewModels / Services）。含「业务拆解」字段，缺则补 `未拆解`，已有日期不要覆盖。
4. 只建结构，不写业务开发文档，除非用户同时要求解析业务。

### 解析业务 <模块> [流程]

交给技能 `dev-parse-biz`。若本命令收到 `解析业务 <模块> [流程]`，按该技能执行。

### 深度拆解 [模块…] [更新]

对整个项目（或点名模块）**逐模块**解析业务，同样交给技能 `dev-parse-biz`，按其批量规则执行。

1. 先按「解析模块」刷新结构与全部 `_模块.md`（补上「业务拆解」字段）。
2. 队列：点名了模块就用点名清单；否则取全部模块，按目录名排序。
3. 增量：跳过「业务拆解」已有日期的模块；带 `更新` 或点名单个模块时强制重拆（更新既有业务文档，不重复建）。
4. 串行：一个模块的全部业务文档写完并更新其 `_模块.md` 的「业务拆解」后，才进入下一个模块。不要并行、不要同时摊开多个模块的代码。
5. 中断续跑：重跑同一命令即可，从第一个「业务拆解」仍为 `未拆解` 的模块继续。
6. 结束汇报：每模块拆出的业务线清单 + 文档路径；没拆完的如实说明停在哪，不要谎报完成。

### 建卡 \<概念\>

沉淀一个公用概念：建 `docs/公用配置/<概念>.md` 概念卡，并把项目里同一概念的不同叫法统一到规范词。

1. **定义来源**（按优先级取，拿不到就问作者，不要编）：
   - 作者在对话里直接给的说明；
   - 从代码与既有开发文档提取：全局搜该概念的相关词，定位模块后读实现，提炼「定义 / 规则」并注明来源文件；读不准的列为假设请作者确认；
   - 业务解析文档里已有现成描述的，直接引用。
2. 按 `references/templates.md` 的「模板：概念卡」代拟草稿（「别名」候选=搜到的变体叫法），**作者确认后**写入 `docs/公用配置/<概念>.md`。
3. **词汇统一**（只改文档，不改代码）：
   - 扫 `docs/开发文档/` 的正文章节（背景 / 需求描述 / 验收标准 / 边界），把该概念的变体词替换为规范名并加 `[[概念名]]` 双链；
   - 时间戳条目（补充需求 / 需求变更 / 缺陷记录）是历史记录，**不回改**，只保证以后新写内容用规范词；
   - 代码里命名不一致（同一概念多个标识符）时，建议作者开一份「术语统一」需求走 通过→开工 流程，不要顺手改代码。
4. 汇报：概念卡路径、别名清单、统一了哪些文档、是否建议代码重命名。

### 接口 \<摄取|变动|比对|列表\>

**先读 `references/interface.md`**（接口文档模板＋摄取/变动/比对/列表细则），按其执行。接口命令不改业务代码；比对只报告，要改代码走 `需求` / `变更`。

### 组件 \<解析|查|登记|影响|比对\>

**先读 `references/components.md`**（组件卡/页面卡模板＋布局草图标记语法＋五子命令细则），按其执行。组件命令不直接改业务代码；注册表漂移与页面布局图检测走 `组件比对`，报告格式与整改纪律同 `references/doc-check.md`。

### 需求 \<任务描述\>

1. 推断模块与目标目录；不确定先问。
2. 按 `references/templates.md` 的「模板：开发文档」新建 `docs/开发文档/<模块>/今天日期-任务名.md`；**状态一律 `待审核`**——即使作者说马上开工也不要写成 开发中/完结，改代码只能由 `开工` 命令触发；来源 `对话`；**目标目录** 填代码路径。对话里的术语已有概念卡的，用 `[[概念名]]` 双链引用（见「公用配置」）。
3. 告诉作者去面板点「调整」或「通过」。不要开工。涉及 UI 的需求，用 `组件查` 标注「优先复用：[[组件名]]」（没有合适的如实写新建）；要修改共享组件的，先跑 `组件影响`，把受影响方写进边界与验收；修改既有业务的需求，从对应业务文档的页面 / 组件双链清单取受影响面写进边界。

### 微改 \<任务描述\>

小改动的**轻量入口**：按 `references/templates.md` 的「模板：微改文档」新建精简开发文档，只保留 基本信息 / 需求描述 / 验收标准 / 交付 四节。省的是写作与阅读成本，**不省流程步骤**——状态机与审批门和 `需求` 完全一致。

**适用**：此前没有归属文档的新小活（改文案、调间距、加一个字段、换默认值）。
**不适用，别用微改**：

- 已交付代码要改 → 走 `需求变更` → `变更`。那份文档的验收标准与交付记录是历史事实，另开微改会让改动与原始需求脱钩，`组件影响`／`整合` 的反查链断掉。
- 交付结果与验收不符（BUG）→ 走 `整改`。微改是新活，`整改` 是返工，语义不同族；混用会往模块卡「缺陷史」灌进没有根因的噪音条目，回归清单失效。
- 波及共享组件、或需要论证边界与非目标 → 走 `需求`。

1. 推断模块与目标目录；不确定先问。
2. 按 `references/templates.md` 的「模板：微改文档」新建 `docs/开发文档/<模块>/今天日期-微改-任务名.md`。**「基本信息」五个字段必须填齐**，尤其：
   - `状态` 一律 `待审核`——即使作者说马上开工也不要写成 开发中/完结，改代码只能由 `开工` 命令触发；
   - `目标目录` 填代码路径；
   - `交付日期` 留空，由 `交付` 填。**不要预先填**：插件靠「交付日期非空」判定该文档已对过代码，提前填会让面板主按钮变成「完结」，跳过审核门。
   - `来源` 填 `微改`，便于事后区分轻量与完整档案。
3. 术语已有概念卡的加 `[[概念名]]` 双链；涉及 UI 的用 `组件查` 标注「优先复用：[[组件名]]」。
4. 告诉作者去面板点「调整」或「通过」。不要开工。
5. 后续与完整档案**同一条流水线**：`开工` → `交付` → 作者「完结」；出 BUG 点「缺陷」走 `整改`；改需求走 `调整`。微改文档没有「边界与非目标」「需求变更」节时，作者记缺陷或变更会由面板自动在文末追加对应章节，不必手工补模板。
6. 完结后同样计入该模块的**未整合欠账**，由 `整合` 并回业务文档——微改不免整合，否则业务文档漂移。批次碎就攒着，`整合` 无参数时会列出所有欠账模块供作者集中处理。

### 添加 \<BUG|变更|补充\> [模块或文档]

**记录入口**：作者口述，AI 落笔——面板「缺陷」「需求变更」「调整」按钮的等价指令。只写记录条目并切换状态，**不改正文、不改代码**；记录后续交给 `整改`/`调整`/`变更` 处理。类型（BUG / 变更 / 补充）缺省或拿不准就问作者，不要猜。

1. 定位文档：点名文档直接用；点名模块取该模块下状态合适的文档；找不到或有歧义就问。**不新建文档**——新活走 `需求` 或 `微改`。
2. 状态门槛与面板一致，不符合就如实说明、不硬记：
   - `BUG`、`变更`：只记**已对过代码**的文档（开发中 / 已交付 / 整改中 / 完结 / 变更中；交付节已填实质内容的也算）；
   - `补充`：只记**需求阶段**的文档（待审核 / 调整中 / 已通过）。
3. 按面板同款格式在该文档对应章节**顶部**插入时间戳条目（`YYYY-MM-DD HH:mm` 分钟级，最新在前；章节不存在时追加到文末；内容多行时每行一条 bullet）：
   - `BUG` → `## 缺陷记录`：`### <时间戳>`＋症状 bullet＋末尾 `- **整改**：` 空占位；状态改 `整改中`。
   - `变更` → `## 需求变更`：`### <时间戳>`＋内容 bullet＋末尾 `- **落实**：` 空占位；状态改 `调整中`（对过代码的两步流：先 `调整` 合入定稿，再 `变更` 落地）。
   - `补充` → `## 补充需求`：`- （<时间戳>）<内容>`；状态改 `调整中`。
4. 记完把插入的条目原文复述给作者核对。**不写 `.ai-review/adjustments/` 桥接 JSON**（那是面板动作的通道）；面板「撤回」只覆盖面板记的条目，AI 记错的条目由 AI 删除并还原状态。

`添加BUG` 是 `添加 BUG` 的快捷写法：只负责把缺陷记进「缺陷记录」，修 BUG 用 `整改`。

### 调整

处理所有状态为「调整中」的开发文档（兼容旧「调整」；素材只认文档里**已记录**的「补充需求」「需求变更」未落实条目与 adjustments/ 桥接 JSON）：按作者的新需求**重新生成这份需求文档**——把意见合并进需求描述/验收标准/边界。**只改文档，不改业务代码。** 清理已处理 adjustments。

完成后按文档阶段改状态：

- **需求阶段**（交付节仍空）→ `待审核`，等作者重新「通过」。
- **对过代码**（交付节有实质内容，或「需求变更」有未落实条目）→ `变更中`，等 `/dev-review 变更` 落地代码。漏改时作者可在面板点「定稿」补上。

**只处理有记录的，不管别的**：没有「调整中」文档、或文档里没有待落实条目时，如实说明并停——不替作者编意见、不代跑其他指令。过程中扫到别的问题（未整改的缺陷、待落地的「变更中」文档）只顺带一句话提示，由作者自己跑对应指令或点面板按钮。

### 开工

对状态 `已通过` 且尚未开发中/已交付/完结/整改中/变更中的文档：立刻改 `开发中`，按验收改 **目标目录** 里的代码。不要改未通过的文档，也不要动已经完结的文档。动代码前先读该模块 `_模块.md` 的「缺陷史」（没有就扫该模块各文档 `## 缺陷记录` 已填「整改」的条目）作回归清单：避开已知坑，改完逐条自查没把旧缺陷重新弄坏。文档里的 `[[概念]]` 双链先解析、读对应概念卡（见「公用配置」），以卡为准；没链接的概念不猜、问作者。写 UI 代码前先查 `docs/组件文档/`（或跑 `组件查`），优先复用已有组件；确需新建的可复用组件，交付时用 `组件登记` 入库。改动波及共享组件时，先跑 `组件影响` 反查全部使用方，改完逐一回归。

### 交付 \<路径或任务名\>

对照验收填同一文档的「交付」节；**交付日期** 填今天；状态 `已交付`。不要另建交付文件。「自测结果」里写明对照该模块「缺陷史」的回归检查（至少覆盖本次改动触及页面的旧缺陷）。本次交付了新的可复用组件时，用 `组件登记` 入库；改动触及页面布局的，重画对应页面卡（槽位增删、图例同步，画法见 `references/components.md`）。交付后提醒作者：该模块的改动之后用 `整合` 并回业务文档（`状态` 命令可见欠账）。

### 整改 [模块或文档]

只修作者**已写进**对应开发文档「缺陷记录」、且「整改」栏还没填内容的条目。**不要替作者编写/编译一份 BUG 文档。**只针对 BUG（交付结果与验收不符）；需求要改：未开工走 `调整`，已过代码走 `变更`。

1. 打开指定文档，或该模块下带未处理缺陷的开发文档（看 `## 缺陷记录` 里还没有填「整改」的条目；状态「整改中」优先）。顺带读该模块 `_模块.md` 的「缺陷史」：症状与旧条相同就是复发。
2. 找不到**有记录缺陷**的文档就如实说明并停：不新建文档，也不把作者随口说的症状自行记成缺陷（记 BUG 走面板或 `添加`）。
3. 条目描述的其实是新需求不是缺陷 → 如实说明并停，建议走 `需求` 或 `微改`，等作者指令；不代跑。
4. 只读与这些缺陷相关的少量代码并改。不要解析整个模块、不要重填交付表、不要走待审核。
5. 在同一条目补上 `- **整改**：`（改了什么）和 `- **根因**：`（为什么会坏、同类代码要避开的点，一两句），状态改回 `完结`。清理已处理的 adjustments JSON。
6. 把每条修复汇入模块卡 `_模块.md` 的「缺陷史」：追加一行 `- YYYY-MM-DD：症状短语 → 根因短语（<任务名>）`；模块卡不存在就按 `references/templates.md` 的「模板：模块卡」新建（只填 目录/文档/缺陷史）。复发时在「整改」行末注明 `复发自 <旧条日期>`。

### 变更 [模块或文档]

处理状态「变更中」的开发文档：变更已由 `调整` 合入文档并定稿，这里只做**代码落地**。**不要新开需求文档，也不要新记变更条目**（记变更走面板或 `添加`）。

**先文档确认，再执行**：文档还在「调整中」就停下，告知作者先跑 `/dev-review 调整` 定稿（或在面板点「定稿」），定稿成「变更中」后再来落地——不要自己串跑 `调整`，更不要跳过文档直接改代码。没有状态「变更中」的文档 → 如实说明并停，不代跑其他指令。

1. 读文档的需求描述/验收标准（已含变更）、`## 需求变更` 里尚未落实的条目，与该模块 `_模块.md` 的「缺陷史」作回归清单。
2. 按文档调整**目标目录**里的代码，完成变更落地（已开工或已完结都直接改，不要再走待审核）。落地后对照缺陷史逐条自查。
3. 在同一条目补上 `- **落实**：`（写了什么）。若原来是开发中则改回 `开发中`，若原来是完结则改回 `完结`。

### 整合 [模块]

把已完结任务的改动**增量并回业务文档**，消除「业务文档过期」。业务文档（`解析业务` / `深度拆解` 的产物）是模块现状的真相，任务文档是过程历史。

1. 范围：点名模块只整合它；无参数则列出所有有未整合任务的模块，与作者确认后逐个做。
2. 收集增量：该模块下状态为 完结 / 已交付、且「基本信息」里没有 `- **已整合**：` 标记的任务文档；取其需求、交付内容、缺陷根因。
3. 合并：把每个任务的改动按目标目录与业务名匹配到对应业务线文档，**原地更新**受影响章节（主流程 / 业务规则 / 分支异常 / 数据依赖）；行为有变但业务文档没有对应章节的，在合适的业务线文档补一节。**整合不了或与现状矛盾的列入待人工确认清单，不要硬改。**
4. **织链（必做，不许跳过，也不许另开清单拖延）**：每份被更新的业务文档确保有「页面 / 组件双链清单」小节（放「边界与非目标」之后）：页面优先双链 `docs/页面文档/` 里真实存在的页面卡（无卡写类名，`组件解析` 建卡后补链）；组件只链 `docs/组件文档/` 里真实存在的卡（未入册的写文件名）；新页面入链、废弃页移除；被链页面卡的「业务」字段要双链回本业务文档（业务↔页面双向）。顺带用代码反查核对涉及组件卡的「使用方」与页面卡图例，过期条目标废弃。**没有织链 = 没整合完。**
5. 盖戳：被整合的任务文档「基本信息」加一行 `- **已整合**：YYYY-MM-DD HH:mm`；`_模块.md` 的「业务整合」更新为 `YYYY-MM-DD HH:mm（n 个任务：任务名…）`。
6. 该模块「业务拆解」仍为 `未拆解`：提示先跑 `解析业务`，本次跳过。
7. 汇报：每模块更新了哪些业务文档、**织链情况（新增 / 更新了哪些双链小节）**、待确认清单、矛盾较多建议 `深度拆解 <模块> 更新` 重拆的模块。

与 `深度拆解` 的分工：整合用任务文档的意图做增量（便宜、快）；`深度拆解 <模块> 更新` 从代码重parse（事实基准）。业务文档与代码矛盾多时用后者。

### 继续

落实已交付文档上的调整意见（代码 + 交付节）。完成后状态改回 `已交付`，请作者再审。

### 状态

扫描 `docs/开发文档/`（及旧 `开发需求/`、`开发交付/`），按模块文件夹分组，指出下一步该谁；同时标出各模块的**未整合任务数**（已完结但没有「已整合」标记的任务）——业务文档的欠账。

### 文档检查 \<模块|整改\>

**先读 `references/doc-check.md`**（报告闭环格式＋六项检查＋整改规则），按其执行：检查只写报告不改文档，整改只按报告修、一律不动状态；页面布局图/注册表漂移归 `组件比对`（见 `references/components.md`），不在这里重复。

## 纪律

- 模板与子命令细则只存在本技能内（SKILL.md＋`references/`，单源不镜像）：改细则改参考文件本体，不在 SKILL.md 复述。
- 开发文档只写 `docs/开发文档/<模块>/`，不写进 `lib/`。
- 「开工」只处理「已通过」，不要改「完结」或作者没点名的文档。
- 状态与指令一一对应：「调整中」→`调整`（只改文档），「变更中」→`变更`（只落地代码），「整改中」→`整改`（只修 BUG）；「开工」才第一次改代码。
- 记录与处理分离：BUG / 需求变更 / 补充需求 由作者经面板按钮或 `添加` 落笔；`调整`/`整改`/`变更` 只处理已记录的条目，没有记录就如实说明并停——不替作者编记录、不代跑其他指令。
- 先文档确认，再执行：对过代码的改动两步走，`调整` 合入定稿在前、`变更` 落地在后；「变更」见到「调整中」的文档要停下等定稿，不许串跑、不许并成一步。
- 「变更」/「整改」不新写文档：作者把内容写在对应开发文档里，技能只读并改。
- 缺陷只针对 BUG，走「整改」，和「调整」「变更」分开。
- `微改` 只是精简模板，不是快捷通道：状态一律 `待审核`、审批门与 `需求` 相同，不要跳过「通过」直接开工；「基本信息」的 状态 / 模块 / 目标目录 / 交付日期 不可省也不可预填（缺字段时面板按钮是空操作、`整合` 捞不到，且不报错）；已交付代码的改动不走微改，走 记「需求变更」→`调整`→`变更`。
- 修复过的缺陷是模块资产：`整改` 必补「根因」并更新模块卡「缺陷史」；`开工`/`变更`/`交付` 必读缺陷史防复发。
- 公用概念以 `docs/公用配置/` 概念卡为准：读文档先解双链、写文档要加双链；概念不明不猜、问作者；概念卡由作者定夺，AI 只代拟草稿。
- 接口文档是外部事实的镜像：正文只由 `接口摄取` / `接口变动` 维护（作者不手改正文，「变更历史」除外）；接口变动要改代码时走 `需求` / `变更`，接口命令不动业务代码。
- 业务文档的时效靠 `整合` 维护：交付/完结攒下的改动由 `整合` 并回业务文档；矛盾列待确认，不硬改。
- 组件文档是复用资产：`开工` 写 UI 前必查、优先复用不重复造轮子；功能雷同的抽取只生成需求走流程；组件文档由 `组件解析` / `组件登记` 维护，标签从受控词表取、新标签提议经作者确认；注册表漂移用 `组件比对` 走报告闭环（`_比对报告.md`，整改只改文档不动代码）。
- 页面卡是索引层：只画槽位、只链接，不复制组件内部布局；图例组件列三态（卡双链 / 文件名 / 样式短语），自绘槽位多是抽组件的信号；织链时业务文档页面链向页面卡、页面卡「业务」链回业务文档。布局草图几何用「布局草图标记」标注——形状潦草无妨，标记必须准，未知标记是检查/比对的报告项。
- 文档规范走报告闭环：`文档检查` 扫描出报告（`docs/开发文档/_检查报告.md`，覆盖重写），`文档检查 整改` 按报告逐项修（不动状态、修完勾选），全部处理完**删报告**；状态漂移等定夺项由作者走面板，AI 不代做。
- 测试结果如实写。
- `_模块.md` 不是任务，不要改它的状态、不要开工它。
