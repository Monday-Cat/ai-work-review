# /dev-review 说明书

**这是什么**：统一开发文档工作流，与 Obsidian「AI Work Review」插件开发模式配合。需求与交付写在**同一份**开发文档里：AI 写需求 → 你在面板「通过 / 调整」→ AI 开工、交付 → 你「完结」。状态与指令一一对应：**调整中**→`调整`（只改文档）、**变更中**→`变更`（只落地代码）、**整改中**→`整改`（只修 BUG）。记录与处理分离：BUG、需求变更、补充需求由你经面板按钮或 `添加` 落笔，处理指令只认已记录的条目——没有记录就如实说明并停。对过代码以后改需求走两步：记「需求变更」→调整中→`调整` 定稿 →变更中→`变更` 落地。

## 命令用法

| 命令 | 时机 | 作用 |
|---|---|---|
| `/dev-review 解析模块` | 首次接入 | 扫描 `lib/features/` 每个业务目录，建 `docs/开发文档/<模块>/` 与模块卡 `_模块.md`（结构索引） |
| `/dev-review 解析业务 <模块> [流程]` | 读懂某个模块 | 把该模块现有业务按业务线拆成开发文档（快照，状态=完结；带 `流程` 则待审核，走审核-开工闭环） |
| `/dev-review 深度拆解 [模块…] [更新]` | 读懂整个项目 | **逐模块串行**解析全部业务：拆完一个（写盘 + 模块卡标记）再下一个；中断后重跑自动续；默认增量，带 `更新` 强制重拆 |
| `/dev-review 组件解析 [模块]` | 建组件库时 | 扫描 widgets 建组件卡（双维标签＋布局 ASCII 草图，受控词表 `_标签.md`）＋页面建页面卡（编号槽位草图＋图例，业务双链）＋按能力分组的 `_索引.md`；雷同组件生成「组件抽取」需求（待审核） |
| `/dev-review 组件查 <需求描述>` | 写 UI 前 | 标签优先定位：能力/场景关键词 → 标签命中 → 推荐＋最小用法；没有合适的直说 |
| `/dev-review 组件登记 <路径>` | 交付新组件时 | 给可复用组件补卡入库 |
| `/dev-review 组件影响 <组件名\|页面名\|路径>` | 改组件/页面前 | 代码反查受影响方（组件卡与页面卡图例交叉核对）＋业务文档双链命中，影响清单＋回归提示；可生成「组件/页面变更」需求（待审核） |
| `/dev-review 组件比对 [模块\|整改]` | 整理完/怀疑漂移时 | 注册表健康检测（**页面布局图缺卡**/孤儿卡/槽位漂移/链健康/织链欠账/使用方核对）→ 写报告 `docs/组件文档/_比对报告.md`（分「AI 可修」「需作者定夺」）；`整改`＝按报告逐项修（只改文档不动代码、修完勾选），全清**删报告** |
| `/dev-review 文档检查 [模块\|整改]` | 怀疑文档不合规时 | 开发文档规范检查（六项：六字段/交付日期预填/微改结构/条目格式/状态漂移/死链）→ 写报告 `docs/开发文档/_检查报告.md`（覆盖重写，分「AI 可修」「需作者定夺」）；`整改`＝按报告逐项修（不动状态、修完勾选），全部处理完**删报告**，定夺项走面板 |
| `/dev-review 需求 <任务描述>` | 开工前 | 把对话需求转写成开发文档（验收标准 checkbox、边界与非目标），状态=待审核 |
| `/dev-review 微改 <任务描述>` | 小改动、无归属文档时 | 精简开发文档（只留 基本信息/需求描述/验收标准/交付），状态=待审核。**只省篇幅不省流程**：基本信息四字段缺了面板按钮空转、`整合` 捞不到且不报错。已交付改代码走 `变更`、BUG 走 `整改` |
| `/dev-review 添加 <BUG\|变更\|补充> [模块或文档]` | 口述要记的内容时 | 记录入口（面板「缺陷」「需求变更」「调整」的 AI 侧等价）：按面板同款时间戳格式把条目写进对应章节顶部并切状态——BUG→整改中、变更/补充→调整中；只写记录，不改正文不改代码 |
| `/dev-review 建卡 <概念>` | 沉淀公用概念 | 建概念卡 `docs/公用配置/<概念>.md`：定义来自对话或从代码/文档提取（AI 代拟、作者确认）；文档里同概念变体词统一为规范名并加双链；代码命名不统一时建议开「术语统一」需求 |
| `/dev-review 接口摄取 <来源> [服务名]` | 拿到接口资料时 | 规范化成 `docs/接口文档/<服务>/_接口.md` 总汇＋原始快照；缺失填「暂无」，名称/说明/Method 可推断经作者确认；JSON 格式化输出 |
| `/dev-review 接口变动 <服务>` | 对方接口更新时 | 重新获取→字段级变动清单→更新接口文档与索引；问询后可生成适配需求（待审核） |
| `/dev-review 接口比对 <服务> [模块]` | 怀疑实现漂移时 | 接口文档对照代码调用点与开发文档，报告三类不一致 |
| `/dev-review 接口列表` | 随时 | 刷新并展示各服务索引（快照日期、接口数、来源） |
| `/dev-review 调整` | 文档状态「调整中」 | 按已记录意见重新生成文档（只改文档）：需求阶段→待审核；对过代码→变更中；**只处理有记录的**，没有就如实说明并停、不代跑 |
| `/dev-review 开工` | 你点「通过」后 | 对「已通过」的文档改代码，状态=开发中；动代码前先读模块卡「缺陷史」防复发 |
| `/dev-review 交付 <任务>` | 功能做完 | 对照验收填同一文档「交付」节，状态=已交付；自测含对照缺陷史的回归检查 |
| `/dev-review 整改` | 你记下 BUG 后 | 只修「缺陷记录」里已记录、未填「整改」的条目，不新开文档、不替你编 BUG；补「整改」「根因」并汇入模块卡「缺陷史」。记 BUG 用 `添加BUG` |
| `/dev-review 变更` | 文档状态「变更中」 | 文档已定稿，按文档落地代码、补「落实」，写回同一文档；还在「调整中」就停下等你先 `调整` 定稿（先文档确认再执行） |
| `/dev-review 整合 [模块]` | 攒了完结任务后 | 把已完结任务的改动增量并回业务文档（原地更新业务线章节）＋**必做织链**（页面/组件双链清单，页面链向页面卡，没织=没整合完）；任务标「已整合」、模块卡盖戳；矛盾列待确认 |
| `/dev-review 继续` | 已交付被调整后 | 落实调整意见（代码 + 交付节），重新交复审 |
| `/dev-review 状态` | 随时 | 按模块列出所有文档卡在哪一步、下一步该谁；含各模块未整合欠账 |
| `/dev-review-info-cn` / `-info-en` | — | 显示本说明书（中/英文） |

## 文件去向

| 位置 | 内容 | 说明 |
|---|---|---|
| `docs/开发文档/<模块>/` | 开发文档（需求+交付同文件） | 审核对象；状态字段被插件跟踪 |
| `docs/开发文档/<模块>/_模块.md` | 模块卡（结构索引） | 记录分层 / 页面 / 职责 / 业务拆解进度与「缺陷史」（已修复缺陷的根因索引，开工/变更/交付前先读）；不是任务，不可开工 |
| `docs/公用配置/<概念>.md` | 概念卡（公用概念） | 双链 `[[概念名]]` 的目标；AI 以卡为准、不猜概念；AI 只代拟草稿、作者确认后落盘 |
| `docs/接口文档/<服务>/_接口.md` | 接口文档总汇 | 外部 API 的规范化镜像；正文只由 接口摄取/接口变动 维护；`_索引.md` 总览 |
| `docs/组件文档/<分类>/<组件名>.md` | 组件卡（复用注册表） | 一组件一卡＋`_索引.md`；开工写 UI 前必查、优先复用；抽取建议只生成需求走流程 |
| `docs/页面文档/<模块>/<页面名>.md` | 页面卡（页面布局索引） | 编号槽位草图＋四要素图例（位置/作用/组件：卡双链/文件名/样式短语）；业务↔页面双向双链；`_索引.md` 总览；`组件解析` 建卡，`组件影响`/`交付` 保鲜 |
| `.ai-review/adjustments/` | 面板「调整」写的意见 | 技能处理时优先读取，处理后自动清除 |

## 工作闭环

```
（可选）深度拆解 / 解析业务 → 读懂现状
/dev-review 需求 → Obsidian 开发模式审：「调整」按新需求重新生成文档 / 「通过」放行
→ /dev-review 开工 → /dev-review 交付 → 你点「完结」
→ 对过代码以后改需求：点「需求变更」（或 /dev-review 添加 变更）→ 调整中 → /dev-review 调整 定稿 → 变更中 → /dev-review 变更 落地代码（AI 忘了改成「变更中」时，面板点「定稿」补上）
→ 是 BUG 点「缺陷」（或 /dev-review 添加BUG）→ /dev-review 整改
```

## 核心规则

1. 需求与交付诚实：测试没过就写没过——你靠文档做批准决策。
2. 状态机把门：只有「已通过」能开工；业务快照固定「完结」，不会被误开工。
3. 业务解析文档必须能对照代码：页面入口、主流程、业务规则、分支异常、数据依赖，读不准的标假设。
4. 公用概念以 `docs/公用配置/` 概念卡为准：文档用双链引用；死链或未定义的概念 AI 停下来问作者，不要猜。

## 适用范围

技能装在项目内（Cursor：`.cursor/skills/`；ZCode：`.zcode/skills/`），管理**本项目**的 `docs/开发文档/`。模块划分默认对应 `lib/features/<模块>`，其他结构的项目按同样规则映射自己的代码目录。
