你执行开发任务的交付审核工作流（配合 Obsidian「AI Work Review」插件）：开工前转写需求档案，完工后写交付单，按作者审核意见继续迭代，直到作者在 Obsidian 面板标记通过。

用户参数：$ARGUMENTS
（第一个词是子命令：`需求` / `交付` / `继续` / `状态`，其余为参数。没有参数时执行 `状态`。）

## 路径约定

- 审核 vault（绝对路径）：`/Users/zhouweijie/Documents/qwen-agent/wuEIEEkpa6/小说`
- 需求档案：`<vault>/开发需求/YYYY-MM-DD-<任务名>.md`（模板：`开发需求/需求模板.md`）
- 交付单：`<vault>/开发交付/YYYY-MM-DD-<任务名>.md`（模板：`开发交付/交付模板.md`）
- 桥接目录：`<vault>/.ai-review/`；作者调整意见在 `adjustments/<镜像路径>/<文件名>.md.json` 的 `note` 字段
- 模板文件本身不要修改。插件面板顶部切到「开发模式」可按任务查看。

## 子命令：需求 <任务描述>

1. 按模板新建 `开发需求/今天日期-任务名.md`，填齐：背景与目标、需求描述（分条）、**验收标准（可验证的 checkbox）**、边界与非目标；状态置 `待开发`。
2. 描述含糊时先向作者确认关键歧义再落档；说清的部分不要反复追问。

## 子命令：交付 <需求文档路径或任务名>

1. 找到需求档案；逐条对照验收标准，有缺口先补齐或如实写明未达成。
2. 按模板新建交付单：状态 `待审核`；完成内容=改动文件清单（改了什么、为什么）；**自测结果=实际执行的命令/测试与结果摘要，没跑的要写明原因，不得编造通过**；验收步骤；风险与遗留。
3. 需求档案状态改 `已交付`，回填关联交付链接。
4. 告诉作者：交付单路径 + 在 Obsidian 面板审核，可点「调整」或在交付单「审核意见」节写意见。

## 子命令：继续

1. 收集意见：① `adjustments/` 下的 JSON；② `开发交付/` 各交付单「审核意见」节有实质内容且未标 `（已处理）` 的条目。
2. 状态为 `已通过` 且无未处理意见的任务直接跳过。
3. 逐条落实：改代码、跑测试、更新文档。**涉及小说 vault 内其他文档（人物库/世界观等）的修改一律走修改稿流程**：整份新内容写 `.ai-review/proposals/<镜像路径>.md`，由作者 diff 确认；交付单与需求档案本身可直接改。
4. 完成后：交付单状态改回 `待审核`、追加本轮修改记录、已处理意见标注 `（已处理）`；删除已处理的 adjustments JSON。
5. 汇总：处理了哪些意见、改了什么、测试结果，请作者复审。

## 子命令：状态

遍历 `开发需求/` 与 `开发交付/`，按任务汇总（需求状态、交付状态、未处理意见数），指出卡点与下一步该谁动作。

## 纪律

- 诚实：测试没过就写没过，未实现就写未实现——作者靠交付单做批准决策。
- 意见处理宁多勿漏；不确定意图时按保守方向执行并说明假设。
- 只写本约定涉及的目录；不碰 `开发需求/`、`开发交付/` 之外的 vault 内容。
